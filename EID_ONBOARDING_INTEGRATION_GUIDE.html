Step-by-step onboarding walkthrough for developer teams and agency portals

Step 1: Prerequisites & Security Compliance Standards

Before applying for credentials, your developer team must ensure that your application conforms to the national eID security guidelines. All onboarding portals must meet the following baseline requirements:

Security Requirements Checklist

  • Enforce HTTPS globally: All callback endpoints must run under TLS 1.2 or TLS 1.3 in production environments. Plain HTTP is strictly forbidden (except for `localhost` during development).
  • Authorization Code Flow with PKCE: Applications must implement Proof Key for Code Exchange (PKCE) to prevent code interception attacks. Implicit flow is deprecated.
  • Secure Client Secrets: Client secrets issued by WSO2 IS must be stored in server-side environment variables (`.env`). Never commit credentials to version control.
  • Claim Release & User Consent: Declare the minimum set of attributes required. For example, if you do not require Tax/CRIB numbers, do not request the BSN claim scope.
⚙️

Step 2: WSO2 Identity Server Configuration

Administrators must register the portal application inside WSO2 Identity Server to configure it as a federated relying party. Follow these console steps:

1

Register Service Provider (SP)

Log in to the WSO2 IS console, click "Applications", select "New Application" and choose "OpenID Connect". Input your portal's display name and client redirect URLs.

2

Configure PKCE and Grant Types

Under OIDC configurations, ensure "Code" is checkmarked, check "Mandatory PKCE", and disable "Implicit Grant" to protect the authentication code exchange.

3

Claim Attribute Mapping

Under the Application's claim configurations, choose mapping dialect `http://wso2.org/claims`. Add required claims: `uin` (Unique ID), `bsn` (Tax/CRIB ID), `email`, and `fullname` to allow token claim release.

Step 3: Portal Codebase Integration

Select your tech stack below to view the standardized integration template configured to execute federated SSO checks against WSO2 IS Broker. 

import NextAuth from "next-auth";
import WSO2Provider from "next-auth/providers/wso2";

export const authOptions = {
  // Central WSO2 Identity Server broker configuration
  providers: [
    WSO2Provider({
      clientId: process.env.WSO2_CLIENT_ID,
      clientSecret: process.env.WSO2_CLIENT_SECRET,
      issuer: "https://localhost:9443/oauth2/token",
      wellKnown: "https://localhost:9443/oauth2/token/.well-known/openid-configuration",
      authorization: { params: { scope: "openid profile email uin bsn" } },
    }),
  ],
  callbacks: {
    async jwt({ token, profile }) {
      if (profile) {
        token.uin = profile.uin; // Unified Identity UIN
        token.bsn = profile.bsn_number; // Tax CRIB Number
      }
      return token;
    }
  }
};
export default NextAuth(authOptions);
// Setup standard OpenID Connect Client configuration
use Jumbojett\OpenIDConnectClient;

$oidc = new OpenIDConnectClient(
    'https://localhost:9443/oauth2/token',
    $_ENV['WSO2_CLIENT_ID'],
    $_ENV['WSO2_CLIENT_SECRET']
);

$oidc->setProviderConfigValue('authorization_endpoint', 'https://localhost:9443/oauth2/authorize');
$oidc->setProviderConfigValue('token_endpoint', 'https://localhost:9443/oauth2/token');
$oidc->addScope(['openid', 'profile', 'uin', 'bsn']);

// Perform auth challenge redirect
$oidc->authenticate();

// Extract federated identity attributes
$uin = $oidc->requestUserInfo('uin');
$email = $oidc->requestUserInfo('email');
using Microsoft.AspNetCore.Authentication.OpenIdConnect;

builder.Services.AddAuthentication(options =>
{
    options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
    options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
})
.AddCookie()
.AddOpenIdConnect(options =>
{
    // Connect program middleware to central WSO2 Hub
    options.Authority = "https://localhost:9443/oauth2/token";
    options.ClientId = builder.Configuration["WSO2:ClientId"];
    options.ClientSecret = builder.Configuration["WSO2:ClientSecret"];
    options.ResponseType = OpenIdConnectResponseType.Code;
    options.SaveTokens = true;
    
    options.Scope.Add("uin");
    options.Scope.Add("bsn");
});

Step 4: Testing & Compliance Verification

Once integration is complete in sandbox settings, testing teams must submit evidence verifying that their application complies with data protection logs:

Testing Verification Rules

  • Audit Trail Check: Trigger a login flow on your portal. Ensure that an Annex E evidence record is automatically generated in the eID dashboard under the Unified Identity logs, detailing the release transaction.
  • Token Token Expiry: Verify that your portal successfully handles session expirations and refreshes access tokens using standard OAuth refresh cycles.
  • Correlation Tracing: Ensure that all API calls route the standardized `x-correlation-id` header to enable transaction trace mappings.
