Why We Maintain the Annex E Audit Trail

Under EU eIDAS (Assurance Level High) and UN/CEFACT citizen protection covenants, identity providers are required to guarantee tamper-proof evidence logs. This audit trail tracks every claim release transaction.

eIDAS Level High

Assurance Compliance

Ensures that any release of core citizen metadata (like CRIB or UIN) to relying parties has a recorded authorization path, meeting legal security standards.

Legal Non-Repudiation

Cryptographic Evidence

By registering the SHA-256 hash of the released payload, both the citizen and the relying party are bound to the transaction. Neither party can deny the data release occurred.

GDPR Transparency

Right to Audit

Citizens have the legal right to trace exactly who accessed their data, when they accessed it, and what claims were released. This dashboard renders these records directly.

Tamper Evidence

Database Integrity

Each log is signed with an absolute transaction correlation key. If database records are modified, the stored payload hash breaks alignment, indicating data tampering.

Where Audit Trail Records are Presented

To ensure total trust, transparency, and auditability, transaction records appear on three distinct layers in our environment:

Citizen Dashboard
Evidence Audit Logs Tab: Citizen-facing logs displaying their personal authentications, OIDC token releases, and WebAuthn signatures to respect GDPR transparency.
Admin Console
Security Audit Logs: System-wide, read-only paginated listing of all identity release transactions. Used by civil registry officers for compliance auditing.
MySQL database
audit_evidence_records table: The persistent backend repository mapped in Entity Framework Core. Stores the correlation keys, verification status, and cryptographic hashes.
⚡

The Transaction Logging Flow

The chronological lifecycle of an audit log transaction starting from a relying party request:

1. Authentication Initiated
A citizen attempts to access a service (e.g. MyGov Portal). The portal redirects them to WSO2 Identity Server.
2. Federated OIDC Request
WSO2 IS acts as the broker and routes the request to our eID platform backend along with a generated request Correlation ID.
3. Citizen Verification (FIDO2)
The citizen authenticates on the eID platform using their cryptographic passkey. The platform verifies the assertion signature.
4. Annex E Logging
Before releasing the claim token, OAuthController calls IAnnexEEvidenceLogger. The service hashes the claim payload and saves the evidence record.
5. Token Release & Session Active
The secure token is released to WSO2, and the citizen is redirected to MyGov with their verified claims. The audit log is now auditable in both dashboards.

Reference ID

Field Schema: VARCHAR(100) NOT NULL

A unique human-readable transactional identifier generated by the eID platform for this claim release. It serves as the receipt number shared with the citizen. 

Value: "EVID-SX-73a8f2cd5c"

Correlation ID

Field Schema: VARCHAR(100) NOT NULL

A GUID mapped directly from the calling federated broker (Keycloak or WSO2 Identity Server). It allows security auditors to link the database log to corresponding WSO2 authentication logs. 

Value: "c892b1a0-d2d1-41e9-91f2-12a809f2d11b"

Timestamp

Field Schema: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

The precise UTC date and time that the transaction was processed, validated, and logged to the MySQL database. 

Value: "2026-07-24 01:21:11"

Subject UIN

Field Schema: VARCHAR(100) NOT NULL

The Unified Identification Number (UIN) of the citizen requesting the credentials check. Serves as the foreign link mapping the record back to the citizen directory. 

Value: "UN-BGD-26-489021-9"

Verification Status

Field Schema: VARCHAR(50) NOT NULL

Details the levels of assurance (LoA) met during the authentication handshake. Standard status outputs are `VERIFIED_HIGH_ASSURANCE` (for passkey/FIDO2 check) and `VERIFIED_SUBSTANTIAL` (for basic logins). 

Value: "VERIFIED_HIGH_ASSURANCE"

Payload Hash

Field Schema: VARCHAR(255) NOT NULL

The SHA-256 cryptographic hash of the JSON claim attributes released to the relying party. This ensures data non-repudiation while respecting privacy by not storing plain text user details directly in logs. 

Hash Algorithm: SHA-256
