System Architecture at a Glance

How components connect during a citizen verification

1

Frontend (Next.js · port 3000)

Citizen-facing registration, login, recovery and dashboard. PSC operator console at /admin/*. All UI calls point to the backend API.

2

Backend API (.NET 8 · port 8082)

All business logic — Civil Registry lookups, UIN generation, OIDC token issuance, MFA, recovery, lifecycle events, audit logs.

3

Civil Registry (Mock Mode by default)

Switchable via appsettings.json → CivilRegistry:Mode. Mock mode uses the seeded records in the same MySQL database. Live mode calls the real Registry HTTP API.

4

MySQL Database (port 3306)

Stores citizens, credentials, civil_registry_records, auth_codes, audit_logs, processed_events, writeback_failures, partial_enrolments.

Before you start

Ensure the .NET API is running: cd eid-with-dotnet && dotnet run --project SintMaarten.EID/SintMaarten.EID.Api --launch-profile http and the Next.js dev server is running: cd eid-frontend && npm run dev

US-4.5 — UIN Tokenisation for Relying Parties

RP receives a token derived from the UIN (not the raw UIN). Different RPs get different token values for the same citizen.

Module 4
How Pairwise Pseudonymisation Works

The platform uses HMAC-SHA256 with a per-client salt to compute TOK-{first16chars}. The same UIN produces different tokens for each OAuth client, preventing RP cross-correlation by default.

1

Get a Token for WSO2 Broker Client

Follow the steps in Scenario 10 (Claims Minimisation) to get an ID Token for eid-wso2-broker-client-id. Decode it and note the sub value.

✅ sub should start with TOK- — NOT the raw UIN like UN-SXM-26-000002-8
2

Verify Different Sub Values for Different Clients

If a second client is registered, the same citizen's token for that client would produce a different TOK-xxxxxxxx value, preventing correlation.

Unique Identity Number (UIN) Engine & International Standards

Citizen lifetime identification algorithm, Luhn Modulus-10 checksum, ISO/IEC 7501 & ICAO Doc 9303 compliance

✓ Standards Compliant

1. UIN Format Anatomy & Structural Breakdown

Standardized identifier structure for Sint Maarten Citizens (UN-SXM-YY-XXXXXX-C)

ISO/IEC 7501-1

The Unique Identity Number (UIN) is a 16-character alphanumeric string generated exactly once per citizen upon birth registration or initial enrolment. It serves as the citizen's permanent legal subject identifier across government registries.

Segment Sample Description & Rules
Prefix UN Universal Identifier Prefix — standard constant for all citizen eID records.
Country SXM ISO 3166-1 alpha-3 Country Code for Sint Maarten.
Year 26 Series Year (YY) — 2-digit year of registration/provisioning (e.g. 26 for 2026).
Sequence 219920 6-Digit Sequential Body — zero-padded unique sequence number (100000 to `999999`).
Checksum 1 Modulus-10 Luhn Check Digit — mathematical integrity digit preventing key-in & transcription errors.
Example UIN String

UN-SXM-26-219920-1

2. Generation Algorithm & Uniqueness Guarantees

Immortality, non-reusability, and cryptographic checksum validation

ICAO Doc 9303
1

Lifetime Immortality & Non-Reusability

Once a UIN is assigned to a citizen (e.g. via Civil Registry birth pre-provisioning or PSC assisted registration), it remains bound to that individual permanently. If a citizen passes away, their UIN is marked as deceased but is never recycled or reassigned to any future citizen.

2

Modulus-10 Checksum Algorithm (Luhn Variant)

The final check digit is computed by applying weight factors [7, 3, 1] across the numeric payload sequence as specified by ICAO Doc 9303 Part 3:

Checksum Calculation Formula: Sequence digits: d₁ d₂ d₃ d₄ d₅ d₆ Weighted Sum S = (d₁×7 + d₂×3 + d₃×1 + d₄×7 + d₅×3 + d₆×1) mod 10 Check Digit C = (10 - S) mod 10 Example for 219920: S = (2×7 + 1×3 + 9×1 + 9×7 + 2×3 + 0×1) = (14 + 3 + 9 + 63 + 6 + 0) = 95 95 mod 10 = 5 Check Digit C = (10 - 5) mod 10 = 5
3

Database Integrity Constraints

Uniqueness is enforced at both application and database engine levels via UNIQUE INDEX constraints on citizens.uin and civil_registry_records.uin in MySQL.

1. Architectural Distinction: UIN vs. eID Credential

Why GoSM separates permanent person identifiers from re-issuable credentials

eIDAS Compliant
Property Unique Identity Number (UIN) eID Credential Identifier (EID)
Binding Bound to Natural Person (Legal Identity) Bound to Physical/Digital Credential Document
Format UN-SXM-26-219920-1 EID-SXM-26-849201-4
Mutability Immutable (Lifetime) — Never changes Dynamic / Re-issuable — Changes upon renewal or loss
Public Exposure Hidden behind TOK-xxxxxxxx pairwise tokens for RPs Present on smart card chip & PSC credential registry
Lifecycle States active, deceased active, pre_provisioned, revoked, suspended

2. Generation Modes & Operational Workflows

Automatic online self-service vs. PSC-assisted operator workflow

⚡ Automatic Online Generation

When a citizen completes remote self-service enrolment (/enrolment) and their details match the Civil Registry database (BSN, NID, DOB), the system automatically provisions an eID credential identifier in active status.

🏛️ PSC Assisted Operator Issuance

For physical eID card issuance at a Public Service Center (PSC), the operator performs biometric baseline capture (face/fingerprint) and ePassport chip verification before issuing the physical smart card with the signed EID-SXM-YY-XXXXXX-C credential.
