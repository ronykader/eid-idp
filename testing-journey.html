System Architecture Overview

The Sint Maarten eID platform integrates with the Civil Registry API to check demographic criteria on registration. The system acts as a secure identity broker with fraud detection capabilities:

1

API-Only Validation Verification

Registration matches data directly with the Civil Registry via HTTP endpoints (no direct DB reads). Latencies exceeding 100ms trigger automated telemetry warnings to satisfy SLA targets.

2

Fraud Detection Holds

Mismatches in name orthography or birthdate block auto-acceptance. The record is flagged as review_pending and locked in the eID database, awaiting physical document verification at the PSC Counter Desk.

3

Automated Write-Back Sync

Upon registration approval (auto or manual), the eID platform performs a writeback to the Civil Registry table, locking the generated UIN and eID Serial Key to that citizen dossier.

🛡️ How Fraud & Identity Theft Prevention Works

To prevent malicious actors from registering accounts using arbitrary or stolen CRIB/NID numbers, the eID platform enforces multi-field demographic cross-checking:

Phase A: Authoritative Lookup

The system queries the Civil Registry with the entered ID (e.g., BSN/NID). The API fetches the official citizen dossier (Name: "John Connor", DOB: "1990-05-15").

Phase B: Demographic Cross-Check

The eID platform compares the form inputs. If the user typed "John Connor Jr." or input a different birthdate, a mismatch is caught. The user's account registration goes on hold (marked "Review Pending") instead of being auto-activated, preventing unauthorized access.

Scenario 10: Claims Minimisation & UIN Pseudonymisation Module 2

Relying Parties only receive claims that are explicitly allowed in their allowed_claims configuration. The citizen's raw UIN and eID are never exposed — instead a pairwise pseudonymous subject token (TOK-xxxxxxxx) is used in all ID Tokens.

WSO2 Broker Client Configuration

Client ID: eid-wso2-broker-client-id
Secret: eid-wso2-broker-client-secret-key-2026
Allowed Claims: email, full_name, dob
Approved Raw: email only
1

Step 1 — Initiate OIDC Authorization

This cURL simulates WSO2 initiating an authorization request. Run it and capture the code from the returned redirect_url.

curl -s -X POST http://localhost:8082/api/v1/oauth/authorize \ -H "Content-Type: application/json" \ -d '{ "client_id": "eid-wso2-broker-client-id", "redirect_uri": "https://localhost:9443/commonauth", "state": "xyz123", "nonce": "nonce-abc", "email": "moderator@eid.sm", "password": "Password123!", "auth_method": "PASSWORD" }'

If the response contains "mfa_required": true, re-run the same cURL adding "otp": "123456" to the body to bypass the MFA challenge.

2

Step 2 — Exchange Code for Tokens

Copy the code value from the redirect_url query string and replace CODE_HERE below:

curl -s -X POST http://localhost:8082/api/v1/oauth/token \ -H "Authorization: Basic ZWlkLXdzbzItYnJva2VyLWNsaWVudC1pZDplaWQtd3NvMi1icm9rZXItY2xpZW50LXNlY3JldC1rZXktMjAyNg==" \ -d "grant_type=authorization_code&code=CODE_HERE&redirect_uri=https://localhost:9443/commonauth"
3

Step 3 — Decode & Inspect the ID Token

Copy the id_token value from the response. Decode its middle segment (base64url) to inspect the JWT payload claims. Use this shell command:

echo 'PASTE_ID_TOKEN_HERE' | cut -d'.' -f2 | tr '_-' '/+' | base64 -d | python3 -m json.tool
4

Step 4 — Verify Assertions

In the decoded payload, verify the following:

CheckExpectedStatus
sub field Starts with TOK- (pairwise pseudonym) ✅ Must NOT be raw UIN
email field moderator@eid.sm (in approved raw releases) ✅ Allowed
electronic_id field Completely absent from payload ✅ Must be ABSENT
uin field Completely absent (raw UIN blocked) ✅ Must be ABSENT
Scenario 11: Authentication Audit Trail Module 2

Every authentication event (login, MFA, recovery, token issuance) is logged to authentication_audit_logs with no raw credentials ever appearing in any log entry. Auditors can retrieve a subject's complete chronological history using the admin query API.

1

Get a Subject UUID

First, login to obtain the moderator's UUID. Run this and copy the uuid from the citizen object in the response:

curl -s -X POST http://localhost:8082/api/v1/auth/login \ -H "Content-Type: application/json" \ -d '{"email": "moderator@eid.sm", "password": "Password123!"}' # → Copy the "uuid" and "access_token" values from the response
2

Query Audit Logs by Subject UUID

Replace TOKEN with the access_token and UUID with the uuid from Step 1:

curl -s \ -H "Authorization: Bearer TOKEN" \ "http://localhost:8082/api/v1/admin/audit-logs?subject=UUID"
3

Verify Expected Audit Events Are Present

The JSON array response should contain at minimum the following action types logged in chronological order:

ActionOutcomeTrigger
LOGINSUCCESSSuccessful password verification
LOGINFAILED_PASSWORDWrong password attempt
MFA_SENDSUCCESSOTP challenge triggered
MFA_VERIFYSUCCESS / FAILED_OTPOTP check result

Verify No Raw Credentials Appear
