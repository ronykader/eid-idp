Chapter 01

OAuth 2.0 Framework

OAuth 2.0 is an industry-standard delegated authorization framework. It specifies protocol flows that enable third-party client applications (Relying Parties) to obtain scoped, limited access to user resources hosted on HTTP services, without requiring the user to disclose their primary password credentials.

Why it is used in Sint Maarten eID

OAuth 2.0 is used to secure API resources (such as backend databases and user profile attributes). By separating authentication from authorization, client applications (like MyGov) request access to resources by exchanging authorization codes for short-lived, cryptographically-signed **Access Tokens** and **Refresh Tokens**. This prevents client portals from ever obtaining or storing raw user credentials.

Core Principles of OAuth 2.0:

  • Role Separation: Splits identity interactions into four logical roles: Resource Owner (Citizen), Client (Relying Party Portal), Resource Server (API database), and Authorization Server (WSO2 / eID engine).
  • Consent-Based Access: Users must explicitly authorize scopes before tokens are generated.
  • Token Cryptographic Scopes: Access scopes (e.g. profile, email) restrict the bearer token's access boundaries.
Chapter 02

OpenID Connect (OIDC)

OpenID Connect (OIDC) is a lightweight identity layer built directly on top of the OAuth 2.0 framework. It extends OAuth 2.0 to provide a standardized mechanism for federated user authentication, introducing a verifiable **ID Token** formatted as a JSON Web Token (JWT).

Why it is used in Sint Maarten eID

While OAuth 2.0 handles authorization, **OIDC** handles federated user authentication (Single Sign-On). It standardizes the identity attributes (Claims) shared between WSO2 IS Broker and relying party applications. Because eID issues standard OIDC claims, any software stack supporting OpenID Connect can immediately configure eID SSO without custom, proprietary adapters.

Core Principles of OpenID Connect:

  • Verifiable ID Token: A signed JWT containing identity assertions (such as sub, email, family_name, given_name, uin).
  • Standard UserInfo Endpoint: Exposes a standardized GET endpoint to query profile attributes using bearer tokens.
  • Well-Known Discovery: Publishes configuration endpoints (at .well-known/openid-configuration) so relying party plugins can auto-discover URLs, key signing endpoints (JWKS), and supported scopes.
Chapter 03

EU eIDAS Regulation

The **eIDAS Regulation (Regulation (EU) No 910/2014)** is a European Union legal framework governing electronic identification and trust services for electronic transactions. It establishes standard criteria to ensure that electronic signatures, seals, time stamps, and identity documents are legally recognized across national borders.

Why it is used in Sint Maarten eID

As a territory within the Kingdom of the Netherlands, Sint Maarten aligns its national digital infrastructure with eIDAS standards. The platform implements **Levels of Assurance (LoA)** (Low, Substantial, and High) defined under eIDAS:

  • Low: Multi-factor SMS/Email validation (suitable for basic portals).
  • Substantial: Authenticator TOTP or verified mobile signatures.
  • High: Passkey WebAuthn (FIDO2) biometric validation linked to passport chips verified by counter clerks.

Key Tenets of eIDAS in eID:

  • Mutual Recognition: Assures that eID credentials issued to Sint Maarten citizens can eventually interoperate with European digital service gateways.
  • Legal Integrity: Enforces strong non-repudiation of transactions by auditing biometric handshakes.
  • Security Controls: Mandates hardware-backed key storage (Secure Enclave, WebAuthn) for high-assurance identity validation.
